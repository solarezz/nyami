# Nyami — аудит текущей архитектуры

Дата: 2026-11-09. Снимок состояния перед большим редизайном/рефакторингом.

## Стек (фактический)

- **Frontend**: React + Vite + TypeScript, Telegram Mini Apps SDK. Вне Telegram работает как обычный сайт в dev-режиме.
- **Backend**: Fastify + TypeScript, без ORM-фреймворка поверх — напрямую Drizzle ORM.
- **DB**: PostgreSQL 16 (свой контейнер в Docker, `docker-compose.yml`), миграции Drizzle Kit.
- **AI**: провайдер-абстрактный слой (`backend/src/ai/`), сейчас Groq (Gemini гео-блокирован в регионе хостинга). Штрихкоды — Open Food Facts → FatSecret fallback.
- **Монорепо**: npm workspaces — `shared/` (общие типы `@nyami/shared`), `frontend/`, `backend/`.
- **Прод**: задеплоено и работает — `nyami.solarezz.dev`, бот `@nyamical_bot`, реальные пользователи.

Размер кода: ~3 800 строк суммарно (backend+frontend+shared). Это сфокусированный solo-dev MVP, уже в продакшене — не прототип и не чистый лист.

## Структура backend (плоская, без доменного разделения)

```
backend/src/
  auth.ts          — проверка Telegram initData (HMAC), dev-bypass вне production
  config.ts
  routes.ts         — все эндпоинты в одном файле
  repo.ts           — интерфейс NyamiRepo + чистые хелперы (даты, стрик, топ частых блюд)
  nutrition.ts       — расчёт BMR/TDEE/БЖУ (Миффлин—Сан Жеор), единственный источник истины
  notifications.ts   — cron-напоминания о пропущенных приёмах пищи
  db/
    schema.ts        — Drizzle-схема, 6 таблиц
    client.ts         — postgres-js клиент (создаётся только при DATABASE_URL)
    repo.ts           — реализация NyamiRepo поверх Postgres
  ai/
    index.ts          — выбор провайдера (AI_PROVIDER=groq|mock)
    groq.ts            — распознавание фото/текста еды, оценка тренировки, коуч-чат
    mock.ts             — детерминированный мок для dev без ключей
    off.ts, fatsecret.ts — поиск продукта по штрихкоду
```

## DB-схема (6 таблиц)

- `users` — профиль + текущие дневные цели (kcal/БЖУ) + стрик + fasting-настройки. PK = `telegram_id`.
- `days` — вода по дням (стаканы). PK = `(telegram_id, date)`.
- `weights` — история замеров веса (timestamped).
- `meal_reminders` — факт отправки напоминания (идемпотентность cron).
- `workouts` — плоская запись тренировки: name/minutes/kcal, без подходов/повторений/веса.
- `meals` — плоская запись приёма пищи: один kcal/protein/carbs/fat на запись, без разбивки на ингредиенты.

## Frontend

8 экранов через простой `useState`-роутер в `App.tsx` (без URL-роутинга): Onboarding, Today, AddFood, AddWorkout, Result, Coach, Progress, Profile. Один глобальный `DataProvider`/`useData` (`data/store.tsx`) — все обращения к API идут через него. Telegram Mini Apps SDK — тема, BackButton; вне Telegram — обычный браузер.

Дизайн (по памяти проекта): светлая тема, тёплый фон, белые карточки, крупные округлые цифры (Nunito), акцент зелёный, кольца БЖУ по цветам — это уже прошло несколько итераций согласования.

## Что уже сделано хорошо — сохранить как есть

1. Расчёт целей калорий/БЖУ — только на сервере (`nutrition.ts`), фронт не дублирует формулу. Соответствует принципу «единый источник бизнес-логики».
2. Telegram `initData` проверяется честным HMAC (`auth.ts`), без доверия неподписанным данным с клиента; dev-bypass жёстко заблокирован в production.
3. AI-провайдер уже абстрагирован (`ai/index.ts`), есть mock-фолбэк — переключение провайдера не требует правок бизнес-логики.
4. Идемпотентные upsert'ы там, где важна гонка запросов (`onConflictDoNothing`/`DoUpdate` при первом создании юзера, при воде).
5. `shared/` пакет держит контракты фронта и бэка в одном месте — на практике расхождений не было.
6. Уже в проде, с реальными пользователями в Telegram — миграции и изменения данных нельзя делать неосторожно.

## Технический долг и пробелы относительно присланного ТЗ

1. **Таймзона захардкожена, не IANA.** Ручной ввод времени тренировки предполагает `+03:00` (MSK) буквально в коде (`db/repo.ts: addWorkout`). Группировка дней/недели — по UTC-календарным суткам, не по локальной дате пользователя. ТЗ §18 требует IANA timezone на пользователя — этого нет нигде.
2. **Еда не разбита на ингредиенты.** `meals` хранит один kcal/БЖУ на запись; нет `food_entry_items`, изменение порции компонента (как «бургер: булочка+мясо+сыр») невозможно. Это прямое требование ТЗ §6.3.
3. **Нет каталога продуктов.** Нет `food_products`/поиска по базе — только AI-распознавание (фото/текст) и штрихкод через внешние API. Нет избранного, нет создания своего продукта с переиспользованием.
4. **Нет рецептов.**
5. **Тренировки — не журнал, а один флажок.** `workouts`: name/minutes/kcal и всё. Нет библиотеки упражнений, подходов/повторений/веса, программ, прогрессии нагрузки — ТЗ §7 описывает полноценный силовой дневник, в коде нет ничего из этого.
6. **Нет измерений тела / фото прогресса.**
7. **Исторические цели не версионируются — реальный баг.** `getDay(userId, date)` всегда подставляет **текущий** `users.dailyKcal`/БЖУ как `goalKcal` для любой запрошенной даты, в том числе прошлой. Если пользователь поменял цель — старые дни в статистике задним числом показывают новую цель, а не ту, что действовала тогда. Нужна таблица `daily_targets` со снимком на дату (ТЗ §12.4).
8. **Расчёт цели — плоский -500/+300 ккал**, без привязки к темпу/тренду/безопасным границам (кроме пола 1200 ккал). ТЗ §9.3/9.5 просит адаптивную корректировку по факту — не реализовано.
9. **Нет отдельного Web-продукта.** Приложение — только Telegram Mini App; браузерный режим — это dev-заглушка для локальной разработки, а не второй полноценный клиент со своей авторизацией.
10. **Тестов нет** — ни unit, ни integration, ни e2e файлов в репозитории не найдено.
11. Backend плоский (`routes.ts`/`repo.ts` — по одному файлу на всё) — на нынешнем размере это нормально; при сильном расширении функциональности это первое, что придётся резать на модули.

## Масштаб vs присланное ТЗ

Присланная спецификация описывает полноценную enterprise-платформу: Telegram + Web как два равноправных клиента с общей авторизацией, модульный монолит на 10 доменов, 20+ таблиц, полноценный силовой тренировочный журнал с библиотекой упражнений и программами, рецепты, фото прогресса тела, адаптивная калорийность по тренду, многоуровневое тестирование. Текущий проект — это ~3 800 строк, один разработчик, уже в проде с живыми пользователями. Сделать весь документ целиком — это реалистично месяцы работы, даже при быстром темпе. Нужно явное решение, какой объём брать в работу сейчас (см. вопрос в чате).
